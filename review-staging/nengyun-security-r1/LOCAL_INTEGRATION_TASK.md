## 必须执行的修改（不能跳步）

### G1：统一配置与生产验证码门禁（C3/C4/C5）

逐个定位所有可将验证码填入生产 `#verify-code` 的实际调用链。所有入口在有副作用之前调用同一个强制守卫；不能继续使用 `cfg.sms || <占位值>` 或等价的跨环境回退。`config.local.json` 缺失、非法 JSON、非法结构、无权限等必须返回分型、脱敏错误，生产不继续提交；主配置损坏亦不得静默降级。测试环境固定码豁免必须被硬性限定为信任的测试合同，不能由本地覆盖为 prod 生效。优先纯函数，CLI 入口转非零退出，新增实际入口级测试。

### G2：统一日志出口（C7）

将原 `ny_log.js` 改为写盘前先生成明确允许字段的安全事件，并用同一对象输出 JSONL/stdout。追踪所有直接 `console.*`、stderr、异常栈、手写 Markdown 和代理生成日志；不能只改 `ny_log.js:63`。不记录任何验证码片段、完整 cookie、账号和密码。合成样本注入测试须检查所有受控出口。

### G3：共享载体事务与状态机（C1/C2/C10）

检查本包 `ny_carrier.js` 和 `ny_sms_state.js` 是否与当前脚本的数据模型兼容；如有差异先修改适配层，不改真实载体。生产脚本的所有写入方必须统一调用事务 API；不允许先 `unlink` 旧文件再 `rename`，不允许按 30 秒锁龄抢锁，也不允许独立写者绕过锁。事务应覆盖读、校验、写、替换及回读。生产记录先绑定 sourceMessageId、请求 ID 和可靠有效期，再由登录尝试原子认领；旧完成回调不能消费新记录，超时未知不能自动重用。`--check` 完全只读。存储备份若存在必须先纳入分发禁止规则。

### G4：分发和审计（C8/C9/C11）

以实际最终打包产物的明确 allowlist 作为主规则，所有运行时文件、备份、临时文件和不认识的文件均不能进入产物；运行 `verify_distribution.js` 作为门禁，实际同步脚本中还需检测别名/符号链接。扫描器只输出规则/文件/行，不输出真实命中值，扫描失败不得 PASS。日志证据按 runId 绑定产物，再独立存放 manifest 摘要；不要夸大抵抗恶意篡改能力。

### G5：验证码双路径（C6）

保留受控人工兜底，但必须与脚本化路径共享阶段、冷却、挑战标识、填入、请求、响应判据和审计字段。人工等待超时/取消必须保证后续未发请求；回调必须可取消；对响应未知不得自动再请求。新模块只是状态契约示例，不能直接当作已接好的浏览器代码。
